# ADR-0053 毎回直す文書はコミットメッセージと todo.md だけにし、ほかはきっかけを決めて直す

- **背景**: 変更を 1 つ入れるたびに、最大で 8 か所に手が入っていた。`Calendared:` のコメント、コミットの本文、customizations.md、todo.md、
  README と日本語の使い方（usage-ja.md）、spec/、ADR とその一覧。10 月からの 265 コミットで、customizations.md は 87 回直されていたのに、読まれてはいなかった。
  書くのはほとんど Claude なので手間は小さく見えるが、人がレビューで読む量が増え、同じことを何か所にも書くので食い違いが起きやすい
- **検討した案**
  - A. 今のまま、決まりを守れているかを道具で確かめる
  - B. 文書ごとに「直すきっかけ」を決め、毎回直すものを減らす
- **決定**: B
  - 毎回: コミットメッセージの本文、todo.md（済んだ項目を消す）
  - 振る舞いの決まりを変えたとき: 機能の仕様（今の features/）の、その機能のファイル。コードやテストを読んでもわからない決まりだけを書き、どのファイルにあるかは architecture.md だけに書く
  - 判断したとき: ADR（基準は今のまま）
  - 作りが変わったとき: architecture.md
  - リリースのとき（パートナーに新しい版を使ってもらうときも）: ルートの README と、Release の説明（使う人から見た変更）
  - やめるもの
    - customizations.md は書き足すのをやめ、archive/ に移す
    - usage-ja.md は消す。パートナーは英語の README を、必要なら翻訳ソフトで読む
    - 元の版から変えた印の `Calendared:` コメントは、新しく付けない。今あるものは残してよい
- **理由**
  - 元の版の更新は取り込まず、独立した版として育てると決めている。元の版から変えた所を見分ける要がなくなったので、customizations.md と `Calendared:` の印は役目を終えた
  - GPL-3.0 の第 5 条 a が求めるのは、改変したことと関係する日付の目立つ表示で、変えた行ごとの印までは求めていない。
    README の Credits（改変した人と、改変を始めた日）と git の履歴で足りる
  - customizations.md の中身は git の履歴とほぼ同じだった。使う人に向けた変更の記録は、リリースのときに Release の説明として書くほうが読まれる
  - usage-ja.md は README の要約で、README と合わせて直す手間が毎回かかっていた
  - A は、守る決まりの数が減らないので、レビューで読む量も食い違いの起きやすさも変わらない
- **結果**
  - development.md の「変更を入れるときの手順」を 8 つから 5 つにし、「文書を直すきっかけ」の表を足した。CLAUDE.md は要点だけにし、development.md を正とした
  - 仕様の文書から、コードの場所の表（stickers.md・migrations.md）、作り直しの経緯（periods.md の「元の作り」）、未決定の案（stickers.md。todo.md の「いつか」へ）を外した。
    state.md は archive/ に移した
  - 同じ日に、初めて読む人が中身を予想できるよう、spec/ を features/（機能がどう動くか）と code/（コードの仕組み）に分け、
    使う人向けの素材は docs/user/screenshots/ から docs/screenshots/ に移した。目次は「知りたいことから探す」表から始める
  - README は、リリースまでの間は今の機能より遅れることがある。リリースの手順に「README が今の機能と合っているかを確かめる」を入れた
