- 見出しは、先頭の「くり返しやること」のあとに進める順（機能を詰める / パートナーに使ってもらう / 公開するか決める / 公開すると決めたら / いつか / 見送ったこと）。不具合か機能かは各項目の頭に書く
- 同じ見出しの中は、上から順に取りかかる。項目を別の見出しに移すのは自由（決めたら日付を添える）
- 終わったものはここから消し、[customizations.md](customizations.md) に 1〜2 行で足して〔日付〕を付ける
- 検討して作らないと決めたものは消さずに「見送ったこと」に移し、理由と、見直すきっかけを残す

2026-10-30 に、進め方を「機能を詰める → パートナーに使ってもらい、フィードバックをもらう → 公開するか決める」にした

## 1. 機能を詰める

わかっている不具合と、作ると決めた機能を片づける。iPhone での確認などで見つかったらここに足す。

### 確かめる

- ペインを閉じたまま日付が変わっても、「今日」が新しくなるか — 自分。2026-11-01 に直した 6 件のうち、日付をまたがないと確かめられない最後の 1 つ
  （ほかの 5 件は 2026-11-01 に Obsidian で確かめた）。Obsidian を開いたまま寝れば確かめられるので、先に仕掛けておく。
  意図: 前は、カレンダーのペインの中のタイマーだけが「今日」を更新していた。今はプラグインが 1 分ごとに確かめる。
  手順: カレンダーのペインを閉じて、Obsidian を開いたまま日付をまたぐ → 翌日、Open now のボタンで今日のノートが開く。
  パンくずのミニカレンダーの「今日」も新しい日になっている

### もう一度起きたら書き足す（再現しないもの）

- 不具合: 書式の欄を確かめていたとき（2026-11-02）、設定を閉じたら、開いていたノートのパンくず・ミニカレンダーが消えていた。
  別のタブに移って戻ると出た。もう一度起きたら、何をした直後かを書き足して「確かめる」の上に「機能・不具合」として戻す

## 4. 公開すると決めたら

### 公開の手続き

決まりと要件、issue の下書きは [guides/publishing.md](guides/publishing.md)。上から順に進める。ただし issue は出したら返事を待つだけなので、
待つ間にほかを進める。「自分」は手でやること（GitHub への書き込み、決めごと、実機の確認）、「Claude」はコードや文書の作業。

- 元の作者の許可（公開すると決めたら、いちばん先。ほかを止める）
  - 下書きを読んで直す。特に、自分の名前・リポジトリの URL・変えたことの一覧 — 自分
  - issue を出す前に、GitHub のリポジトリを公開にするか決める（元の作者が改変の中身を見られるほうが判断しやすい。公開にしないなら、
    下書きからリポジトリへのリンクを消す）— 自分
  - issue を出す — 自分
  - 返事を待つ。許可が出たら、issue へのリンクを README のクレジットに書く。30 日たっても返事がなければ、B の形で進める — 自分
- `versions.json`（どの版がどの `minAppVersion` から動くかの対応表）を作るか決める。任意 — Claude
- リポジトリの整理
  - 既定のブランチを決める（`custom` のままか、`main` にするか）。審査は既定のブランチの先頭の `manifest.json` を読む — 自分
  - `upstream` の remote を、元のコードを見比べる参照用に残すか決める — 自分
  - GitHub のリポジトリ（small-spring/calendared）を公開にする。2026-10-30 の時点では外から見えない。README とライセンス表示が済んでから — 自分
- 確かめる
  - `npm test`・`npm run build`・`npm run deploy` が通る — Claude
  - Release から入れて動くか。BRAT でこのリポジトリを指定して入れるのが手軽 — 自分
  - 絵文字の検索の言語を、本番の版で jsDelivr から追加できるか（リポジトリを公開にしてから。取れないときに GitHub の raw から取れるかも）— 自分
- 申請（手順は guides/publishing.md の「申請の手順」）
  - Release を作る。`manifest.json` の `version` と同じタグを push すると、ワークフローが下書きを作る（[guides/development.md](guides/development.md) の「Release」）— 自分
  - community.obsidian.md でプラグインを登録する — 自分
  - 自動の審査で指摘されたら直す — Claude と自分
- 公開が済んだら、文書を切り替える — Claude
  - [customizations.md](customizations.md) を「公開までの改造の記録」として [archive/](archive/) に移し、以後の変更は英語の `CHANGELOG.md` に書く
    （GPL-3.0 の「改変したことと日付」は、README の告知・CHANGELOG・archive の記録で示し続ける）
  - [guides/publishing.md](guides/publishing.md) を archive/ に移し、毎回のリリースの手順を guides/release.md に書く

### 公開のあと、早めに

- フォーラムの「Share & showcase」や Discord の `#updates` で知らせる（任意）— 自分

## 5. いつか（必要になったら・要望が出たら）

### ステッカー

- ステッカーを複数の種類に（例: 気分 `mood`、活動量 `activeness`）
  - 種類ごとにプロパティを 1 つ持ち、それぞれに絵文字を 1 つ付ける。カレンダーに出す種類を切り替える
  - 前に見送った「1 つのノートに複数のステッカーを並べる」とは別の考え（表示は常に 1 つなので、マスの表示を考え直さなくてよい）
  - [ADR-0001](adr/0001-sticker-in-one-property.md)（プロパティ 1 つ）を「種類ごとにプロパティ 1 つ」に広げる形。付ける操作（ピッカー）でどの種類かを選ぶ方法を考える
  - 種類ごとの設定（絵文字の選び方: すべてから / 候補を先頭に / 候補だけ）と付ける UI の案は [plans/sticker-kinds.md](plans/sticker-kinds.md)
- カレンダーの日付（や月）をダブルクリックして、ステッカーのピッカーを開く（近道）
  - そのノートを開いているときだけ有効にする。開いている日付のクリックは同じノートを開き直すだけなので、
      ダブルクリックをピッカーに割り当てても余計なことが起きず、ふだんのクリックも遅れない
  - 判定は「1 回目のクリックの時点で、すでに開いていたか」で行う（まだ開いていない日付を癖でダブルクリックした人にピッカーを出さない）
  - 隠れた操作なので、見える入口（見出しバーのボタン、コマンド、カレンダーの右クリック）の近道という位置づけ。スマホのダブルタップは要確認
- 絵文字ピッカーの乗り換え: 候補は emoji-picker-element（多言語のデータ emojibase で検索できる）。emoji-mart の更新が止まって困ったら

### 周期とノート

- 日・月のノートの名前を年度で書く（年度の年と四半期の記号を足す）。今は日・月の書式に `Q` を使えない（[ADR-0040](adr/0040-format-tokens-per-period.md)）。
  見直すきっかけ: 年度で名前を付けたいという声が出たら（パートナーに聞く）
- 学期（年を 2 つや 3 つに分ける）。四半期では表せない。要望が出たら考える
- 1 つの周期に、書式の違うデイリーノートを何種類も持てるようにする（例: 日記と作業ログ）
  - 2026-10-31 に書式を周期ごとに 1 つにした（[ADR-0019](adr/0019-one-format-per-period.md)）。複数の種類を使う人は、ほしくなるまで想定しない
  - 作るなら、書式だけでなく、種類ごとにフォルダ・テンプレートも持つ形にする。新しく作るときに、すべての種類をさっと作れる UI にする
  - 決めること: カレンダーは 1 日 1 ノートの作りなので、日付を押したときにどれを開くか、ステッカーや印をどれから取るか、パンくず・ミニカレンダーがどれを指すか
  - 設定の形は `periods.<周期>.format`（文字列 1 つ）なので、種類の一覧に広げるときは読み込むときに読み替える

### 移行

- 中身を書き換える移行（2026-10-30 に、同梱する移行はファイルの中身を書き換えないものだけにすると決めた。[spec/migrations.md](spec/migrations.md)）
  - 同じ日の 2 つのノートを 1 つにする: 書式の変換で名前がぶつかったとき。決めること: 付けるときの区切り（見出しや区切り線）、
    プロパティがぶつかったときの扱い、1 つにしたあと前のノートをどうするか
  - フォルダの移し替え: 中身は変えないので、書式の変換と同じ形で足せる
  - 元の版のステッカー（本文のタグ）をプロパティに移す
    - 書き換える前に、対象のノートと変更内容の一覧を見せる。ステッカーのつもりでないタグを書き換えないよう、対象を選べるようにする
  - 自分の Vault の移行はスクリプトとバックアップで行う。そこで起きたぶつかり方を、1 つにする機能を作るときの材料にする
- 移行の種類を足すときは、先に移行の画面の書式とステッカーの行（`plugin-tab.ts` の `renderFormatMigration`・`renderStickerMigration`）を
  1 つの形にする（2026-11-01 の共通化では残した: 文言・計画の形・入力欄が違い、行の形を決め直す必要があり、設定画面にはテストもない）— Claude

### 移動と表示

- 月をいちばん短い周期で使う人に、ふつうのカレンダー（日付の表）も見せる（2026-11-01 に月の一覧にすると決めた。[ADR-0043](adr/0043-month-list-for-month-users.md)）。
  見直すきっかけ: そういう人から、ふつうのカレンダーが見たいという声が出たら（パートナーに聞く）
- 年のビューの 12 年の区切りを、今年を基準にする（過去を多めに。例えば今年が 3 段目に来るようにする）。今は 2020 起点の固定の区切り
  （`YEARS_RANGES_START`）なので、2031 年には今年が最後のマスに、2032 年には最初のマスに来て、残りがノートのない未来になる。
  1 月 1 日に区切りが 1 年ずれるが、日付が変わったときの更新（`src/today.ts`）に乗せられる。年のビューが出るのは年だけを使う人なので急がない
- 月・年のビューで、開いているノートを含む月（年）のマスを、開いている週の行と同じ薄い帯で塗る。「開いているノートの期間を、表のマスの細かさで塗る」
  という 1 つの決まりにし、週の行の帯もそれで書く（案は [ADR-0043](adr/0043-month-list-for-month-users.md)）。
  見直すきっかけ: 日・週をオフにした使い方で、開いているノートがカレンダーのどこかわからないと感じたら
- 「カレンダーは開いたノートに付いてこないでほしい」設定（2026-10-29 に設定「Auto-sync calendar date」ごと削った）。
  別の月を見たままほかの場所からノートを開く使い方で困る人がいたら、設定を足し直すか考える
- フローティング表示・プレビュー欄を作り直す（2026-10-29 に一度削ると決めたもの。優先度低）
  - プレビューを作るなら、Obsidian 標準のホバープレビュー（コアプラグイン「ページプレビュー」。エクスプローラーでファイル名にホバーすると出るもの）と
    一貫した形にする。先にその機能と、オン・オフの設定のしかたを調べる
  - 今のカレンダーのホバー（`src/ui/utils/event-handlers.ts` の `onHover`）は、その標準機能を `hover-link` イベントで呼んでいるだけ。
    出所「Calendared」を登録しているので、Ctrl/Cmd が要るかはページプレビューの設定画面で切り替える（[ADR-0026](adr/0026-hover-preview-via-page-preview.md)）
- 自然言語の日付（「来週の金曜」でノートを開く、テンプレートの `{{next friday}}`）を作り直す（2026-10-29 に一度削ると決めたもの。優先度低）

### TODO

- TODO 管理（作り直し。すぐには使わないので急がない）: 今の「TODO の引き継ぎ」を消したうえで、欲しい形を考えてから作る
  - 今の作り（`src/io/utils.ts` の `extractAndReplaceTODOItems`）: ノートを作ったとき、前の期間のノートの `## TODO` の下の未完了の
    `- [ ]` を、新しいノートの `## TODO` の下に書き写す
  - 今の作りの問題点（作り直すときに避ける）:
    - 既定でオン（`## TODO`）なので、知らないうちにノートが書き換わりうる。設定がプレビューの設定の中にあって見つけにくい
    - 前のノートがなければ最大 3 つ前まで遡る（数に根拠がない）。前のノートからは消さないので、同じ項目が古いノートに残り続ける
    - 字下げ（入れ子のタスク）を消して平らにする。`* [ ]` や番号付きは拾わない。`## TODO` の下に小見出しがあるとそこで止まる。
      見出しの判定が前方一致なので `## TODOs` なども拾う
    - ほかのプラグイン（Templater、コアのデイリーノート）が作ったノートにも、作られた瞬間に書き込む。Templater の書き込みとぶつかりうる
    - ファイルの末尾の改行を消す
  - 例: 前のノートの未完了を引き継ぐ（コマンドで明示的に、など）、カレンダーに未完了の数を出す
  - 方針: 作るなら、いろいろな使い方に合わせられるようにする（見出しの深さ `### TODO`、見出しの名前、置き場所など）。
    「Calendared の TODO」と呼べるだけのアイデア（カレンダーや周期ノートと組み合わせてこそ便利なもの）が出たら作る。
    出なければ作らず、既存のプラグインを使う
  - 作る前に既存の TODO 系プラグインを調べる。よく知られているもの（調べる前の手がかり）:
    - Tasks: ノートのどこにでも書いたタスクに期日・繰り返しを付け、クエリで一覧にする
    - Rollover Daily Todos: 前のデイリーノートの未完了を新しいデイリーノートへ移す（今の「引き継ぎ」に一番近い）
    - Dataview: タスクをクエリで集める（Vault ですでに使っている）
    - Kanban、Day Planner、Todoist Sync など

## 見送ったこと

- 開いている設定画面を、テンプレート・フォルダのファイルの変化に付いていかせる（2026-11-02）: 開いたまま消しても、開き直すまで
  前の表示が残る。コアのデイリーノートも同じで、保存された設定は正しく扱われる。見直すきっかけ: 古い表示にとまどったら（[ADR-0049](adr/0049-template-path-as-is.md)）
- 元の版の書式の一覧を 1 つにしたときの移行の知らせ（2026-11-01）: 元の版で 1 つの周期に書式を 2 つ以上登録していた人が乗り換えると、
  捨てた書式の名前のノートがカレンダーから消えるが、書式を変えたときの警告（[ADR-0035](adr/0035-migration-notice.md)）は出ない。
  今は当てはまる人がいない。見直すきっかけ: 公開すると決めたら
- ほかのプラグイン（コアのデイリーノート、Periodic Notes）の設定の読み取り（2026-10-31）: 黙って読むと「読み取った」という知らせを
  いつ消すかが決まらず、聞く形は入れた直後にはわかりにくい。設定は数か所なので手で合わせられる。見直すきっかけ: 乗り換える人から
  手で合わせるのが面倒という声が出たら、移行のサブページに「取り込む」ボタンとして足す（[ADR-0034](adr/0034-no-settings-import.md)）
- 「Open now」のコマンド（2026-10-30）: 日を使う人には「Open today's note」と同じなので作らない。見直すきっかけ: 日を使わない人から、
  ホットキーで今に行きたいという声が出たら（[ADR-0030](adr/0030-open-now.md)）
- 週の決め方を選べるようにする（2026-10-30）: 火曜など土・日・月以外の週の始まり、1 月 1 日を含む週を第 1 週にする、年で切る週など。
  ISO の週番号と土・日・月の始まりで足りると考え、設定の「週の決め方」の欄も消した。見直すきっかけ: ISO 以外の週番号が欲しいという
  要望が出たら（[ADR-0014](adr/0014-swappable-week-scheme.md)。期間の計算は週の決め方の部品に集めてあるので、部品を 1 つ足せばよい）
- 「昨日・明日のノートを開く」コマンド（2026-10-29）: 「Open today's note」→「Open previous/next periodic note」の
  2 回で届くので作らない。見直すきっかけ: 今日のノートを経ずに明日へ行くことが多いと感じたら、`tomorrow` / `yesterday` の名前で作る
  （月なら「last month's / next month's」と言えるので、名前は作らない理由にはならない）
