# これからやること

作る・直す作業の一覧。公開の手続き（元の作者の許可、ライセンス表示、manifest、README、申請）は [publishing.md](publishing.md) にある。

- 見出しは「いつまでにやるか」で分ける（公開までに / 公開後、早めに / いつか / 見送ったこと）。不具合か機能かは各項目の頭に書く
- 同じ見出しの中は、上から順に取りかかる。項目を別の見出しに移すのは自由（決めたら日付を添える）
- 終わったものはここから消し、[customizations.md](customizations.md) に 1〜2 行で足して〔日付〕を付ける
- 検討して作らないと決めたものは消さずに「見送ったこと」に移し、理由と、見直すきっかけを残す

## 1. 公開までに（必須）

2026-10-30 に、わかっている不具合を直してから公開すると決めた。同じ日に、「公開後、早めに」にあった 4 つもここに移した
（公開の手続きは [publishing.md](publishing.md)。iPhone での確認などで見つかったらここに足す）。

- 〔機能〕設定画面の整理（機能の整理が終わったら）
  - 「Open on startup」は各周期の設定に散らばっているが、実際は 1 つしか選べない（オンにするとほかは自動でオフ。起動時は日→週→月→四半期→年の
    順で最初の 1 つを開く）。周期ごとのトグルをやめ、全体の設定に「起動時に開く: なし / 日 / 週 / 月 / 四半期 / 年」の選択肢を 1 つ置く（2026-10-29 にメモ）
  - 今は「Calendar」と「Periods」のタブがあり、「Calendar」タブの中にステッカー・タイムライン・プレビューなどの設定が詰め込まれている
  - 機能ごとの階層構造を考え直して、タブや見出しを組み直す
  - 書式の設定を、役目ごとに分けて考え直す（2026-10-30 にメモ）。今は 1 つの書式の一覧が 3 つの役目を兼ねていて、わかりにくい
    - 新しく作るノートの名前を決める書式（1 つ）、すでにあるノートを読み取るための書式（いくつでも）、
      古い書式のノートを新しい書式の名前に付け替える移行（「3. いつか」の移行の項目）
    - 使いやすく、迷わず、設計としてもきれいな形にする。たとえば「作る書式」と「読み取る書式」を別の欄に分け、移行は別の場所にまとめる
  - Obsidian 1.13 からの、設定画面を宣言で書く仕組み（`getSettingDefinitions()`）に乗せ換えるかも考える（2026-10-30 に調べた）。
    乗せ換えると、設定の検索や、公式の一覧の形（`type: 'list'`: 行を詰めた見た目、消すボタン、空のときの文言、パソコンでは見出しの「＋」・
    スマホでは一覧の下の「＋ 名前」の行）が使える。ただし今の設定画面は Svelte で全部自分で描いているので、一覧だけは差し込めず、タブ全体の
    書き直しになる（複雑な部分は `render` で手描きを混ぜる）。`minAppVersion` を 1.13 に上げるか、古い版向けの書き方も持つ必要がある
  - 絵文字の検索の言語の一覧（`EmojiLanguages.svelte`）は自前の見た目にした。公開の部品 `SettingGroup`（1.11 から）で公式の一覧の配置を
    まねた版と見比べて、自前の版を選んだ（2026-10-30）。見直すときは、Obsidian の一覧の見た目とずれていないかも見る
- 〔文書〕ショートカットのおすすめを示す（2026-10-30 にメモ）: 既定のホットキーは付けない（公開のガイドラインに従う）代わりに、
  README などに「おすすめのキーの割り当て」を載せる。例: 今日のノート Cmd+D、前後のノート Cmd+← / →、今月のノート Cmd+M、
  カレンダーの表示 Cmd+Shift+C（自分の Vault の割り当て）。Cmd+← / → は編集中の行頭・行末への移動と重なることも書き添える

## 3. いつか（必要になったら・要望が出たら）

- ステッカーを複数の種類に（例: 気分 `mood`、活動量 `activeness`）
  - 種類ごとにプロパティを 1 つ持ち、それぞれに絵文字を 1 つ付ける。カレンダーに出す種類を切り替える
  - 前に見送った「1 つのノートに複数のステッカーを並べる」とは別の考え（表示は常に 1 つなので、マスの表示を考え直さなくてよい）
  - [stickers.md](stickers.md) の ADR-001（プロパティ 1 つ）を「種類ごとにプロパティ 1 つ」に広げる形。付ける操作（ピッカー）でどの種類かを選ぶ方法を考える
- ステッカー関連
  - カレンダーの日付（や月）をダブルクリックして、ステッカーのピッカーを開く（近道）
    - そのノートを開いているときだけ有効にする。開いている日付のクリックは同じノートを開き直すだけなので、
      ダブルクリックをピッカーに割り当てても余計なことが起きず、ふだんのクリックも遅れない
    - 判定は「1 回目のクリックの時点で、すでに開いていたか」で行う（まだ開いていない日付を癖でダブルクリックした人にピッカーを出さない）
    - 隠れた操作なので、見える入口（見出しバーのボタン、コマンド、カレンダーの右クリック）の近道という位置づけ。スマホのダブルタップは要確認
  - 元の版のステッカー（本文のタグ）をプロパティに移す移行機能を、ステッカー機能とは別に作る
    - 書き換える前に、対象のノートと変更内容の一覧を見せる。ステッカーのつもりでないタグを書き換えないよう、対象を選べるようにする
- 移行（既存のノートの名前を、新しい書式に付け替える）を、書式の切り替えとは別の機能として作る（2026-10-29 に、切り替えと移行を分けると決めた）
  - 置き場所や形は、「1. 公開までに」の設定画面の整理（書式の設定を役目ごとに分ける）で一緒に決める（2026-10-30）
  - 今は、新しい書式の行の「ほかの書式のノートを、この書式の名前に付け替える」ボタン（元の版の機能。週の読み違いとリンク切れは直した）で代わりになる
  - 作るときに考えること: 切り替えた直後に「古い書式のノートが N 件ある」と知らせて移行へ案内する、付け替えの前に一覧（変わる名前）を見せる、
    移行が済んだら古い書式を消せると案内する
  - 置き場所（2026-10-29 の案）: 設定画面に移行をまとめる場所（「移行・メンテナンス」の見出しなど）を作り、ほかの移行（元の版のステッカーのタグを
    プロパティへ）と並べる。あわせて、古い書式を × で消すときの確認にも「この書式でしか読めないノートが N 件。先に付け替えますか」と出して、
    そこから移行に進めるようにする
- プラグインの文言（設定画面、コマンド名、通知）を訳す。今は英語だけ。訳すなら文言を 1 か所に集めて英語・日本語の 2 つから始める。
  公開するなら英語が基本で、日本語は後からでよい
- 「カレンダーは開いたノートに付いてこないでほしい」設定（2026-10-29 に設定「Auto-sync calendar date」ごと削った）。
  別の月を見たままほかの場所からノートを開く使い方で困る人がいたら、設定を足し直すか考える
- TODO 管理（作り直し。すぐには使わないので急がない）: 今の「TODO の引き継ぎ」を消したうえで、欲しい形を考えてから作る
  - 今の作り（`src/io/utils.ts` の `extractAndReplaceTODOItems`）: ノートを作ったとき、前の期間のノートの `## TODO` の下の未完了の
    `- [ ]` を、新しいノートの `## TODO` の下に書き写す
  - 今の作りの問題点（作り直すときに避ける）:
    - 既定でオン（`## TODO`）なので、知らないうちにノートが書き換わりうる。設定がプレビューの設定の中にあって見つけにくい
    - 前のノートがなければ最大 3 つ前まで遡る（数に根拠がない）。前のノートからは消さないので、同じ項目が古いノートに残り続ける
    - 字下げ（入れ子のタスク）を消して平らにする。`* [ ]` や番号付きは拾わない。`## TODO` の下に小見出しがあるとそこで止まる。
      見出しの判定が前方一致なので `## TODOs` なども拾う
    - ほかのプラグイン（Templater、コアのデイリーノート）が作ったノートにも、作られた瞬間に書き込む。Templater の書き込みとぶつかりうる
    - ファイルの末尾の改行を消す
  - 例: 前のノートの未完了を引き継ぐ（コマンドで明示的に、など）、カレンダーに未完了の数を出す
  - 方針: 作るなら、いろいろな使い方に合わせられるようにする（見出しの深さ `### TODO`、見出しの名前、置き場所など）。
    「Calendared の TODO」と呼べるだけのアイデア（カレンダーや周期ノートと組み合わせてこそ便利なもの）が出たら作る。
    出なければ作らず、既存のプラグインを使う
  - 作る前に既存の TODO 系プラグインを調べる。よく知られているもの（調べる前の手がかり）:
    - Tasks: ノートのどこにでも書いたタスクに期日・繰り返しを付け、クエリで一覧にする
    - Rollover Daily Todos: 前のデイリーノートの未完了を新しいデイリーノートへ移す（今の「引き継ぎ」に一番近い）
    - Dataview: タスクをクエリで集める（Vault ですでに使っている）
    - Kanban、Day Planner、Todoist Sync など
- フローティング表示・プレビュー欄を作り直す（2026-10-29 に一度削ると決めたもの。優先度低）
  - プレビューを作るなら、Obsidian 標準のホバープレビュー（コアプラグイン「ページプレビュー」。エクスプローラーでファイル名にホバーすると出るもの）と
    一貫した形にする。先にその機能と、オン・オフの設定のしかたを調べる
  - 今のカレンダーのホバー（`src/ui/utils/event-handlers.ts` の `onHover`）は、その標準機能を `hover-link` イベントで呼んでいるだけ。
    出所を `source: "preview"`（借り物）にしているので、ページプレビューの設定画面に Calendared の項目が出ない。
    `registerHoverLinkSource` で自分の出所を登録すれば、標準の設定画面でカレンダーのオン・オフ（Ctrl/Cmd 必須かどうか）を切り替えられるはず。
    今ある設定「Hover preview」（`autoHoverPreview`）との関係も合わせて考える
- 自然言語の日付（「来週の金曜」でノートを開く、テンプレートの `{{next friday}}`）を作り直す（2026-10-29 に一度削ると決めたもの。優先度低）
- 絵文字ピッカーの乗り換え: 候補は emoji-picker-element（多言語のデータ emojibase で検索できる）。emoji-mart の更新が止まって困ったら

## 見送ったこと

- 「昨日・明日のノートを開く」コマンド（2026-10-29）: 「Open today's note」→「Open previous/next periodic note」の
  2 回で届くので作らない。見直すきっかけ: 今日のノートを経ずに明日へ行くことが多いと感じたら、`tomorrow` / `yesterday` の名前で作る
  （月なら「last month's / next month's」と言えるので、名前は作らない理由にはならない）
- 週の決め方を選べるようにする（2026-10-30）: 火曜など土・日・月以外の週の始まり、1 月 1 日を含む週を第 1 週にする、年で切る週など。
  ISO の週番号と土・日・月の始まりで足りると考え、設定の「週の決め方」の欄も消した。見直すきっかけ: ISO 以外の週番号が欲しいという
  要望が出たら（[periods.md](periods.md) の ADR-006。期間の計算は週の決め方の部品に集めてあるので、部品を 1 つ足せばよい）
